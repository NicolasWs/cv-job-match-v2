## 1. Problem

NIC-46/NIC-47 built and shipped a fully working Notion file-attachment mechanism (`scripts/notion_cv_attachment.py`, `scripts/notion_cover_letter_attachment.py`), but both tickets explicitly flagged — and both `docs/ARCHITECTURE.md` and QA evidence confirm — that they were verified using small, hand-constructed **synthetic PDFs**, not real output from the v1 repo's `cv-match` or `write-outreach` skills. This ticket closes exactly that gap: produce a genuine, well-laid-out PDF from each skill's real markdown output and prove it flows into the already-shipped attachment mechanism unmodified.

## 5. Key design point 1: PDF library/tooling decision

**Decision: use `reportlab` directly (or via the existing `pdf` skill's `pdf_create.py` CLI as a building block) as the markdown → PDF renderer. Do not use LibreOffice/`soffice` headless conversion as the primary path.**

Rationale, weighing what's actually available:

| Option | Available here? | Verdict |
|---|---|---|
| `reportlab` (direct, or via `pdf` skill's `pdf_create.py`) | **Yes** — already installed and backing a shipped, working skill CLI in this environment. Pure Python, no external binary. | **Recommended.** Matches this repo's established style (NIC-46/47 explicitly praised "no Notion SDK, no third-party HTTP library — pure stdlib" as a design virtue); a pure-Python renderer with no subprocess/binary dependency is the same philosophy. Full control over layout (headings, spacing, inline bold/italic via reportlab's Paragraph XML-subset markup) — the right tool for "clean layout, not raw text dump." |
| `python-docx` (via `docx` skill's `docx_create.py`) + `soffice --headless --convert-to pdf` | Partially — `python-docx` is available in a v1-repo-local venv only (not a v2-repo dependency); `soffice` **is** installed system-wide. There is a real, manual, one-off precedent for this exact chain (`cv-spec.json` → `.docx`, done by hand once for UpSlide). | **Rejected as primary, documented as a fallback only.** Introduces an external-process dependency (LibreOffice headless conversion) and an intermediate `.docx` artifact for no layout benefit over reportlab for this document type (CV/cover letter are single-column, heading+paragraph+list documents — exactly what `pdf_create.py`'s element model already handles). Slower per-render (spawns a LibreOffice process), and Builder would need to set up a v2-repo Python environment with `python-docx` where none currently exists, whereas `reportlab` is already reachable via the `pdf` skill with zero new setup. |
| `pandoc`, `wkhtmltopdf`, `weasyprint`, any hosted markdown-to-PDF API | **No** — none installed; the hosted-API option is explicitly forbidden by the ticket without separate validation. | **Rejected.** Would require a new system install (violates "check what's already available before recommending a library") or a forbidden third-party service call. |

**Concretely:** the new `scripts/render_markdown_to_pdf.py` (v2 repo) should:
1. Parse the input markdown with a small, dependency-free translator (stdlib `re`, matching this repo's existing "no new third-party dependency" discipline from `notion_attachment_naming.py`) into the same JSON element list `pdf_create.py` already consumes (`heading`/`paragraph`/`table`/`pagebreak`), converting `**bold**`/`*italic*` markdown spans into reportlab's inline `<b>`/`<i>` Paragraph markup (reportlab's Paragraph supports this HTML-like subset natively — no separate rendering pass needed).
2. Either shell out to the already-shipped `pdf_create.py` CLI with the generated spec, or import and call reportlab platypus directly inside the new script (Builder's implementation choice — both stay within the same dependency, no new library either way).
3. Not require a new virtualenv in the v2 repo if `reportlab` is reachable from wherever `pdf_create.py` already runs from (same interpreter/environment the `pdf` skill uses) — Builder must verify and document exactly which Python environment/interpreter is used, since the v2 repo currently has no `requirements.txt`/venv of its own (confirmed empty in this investigation).

## 6. Key design point 2: PDF layout/quality bar

### 6.1 Tailored CV PDF — minimum bar (testable, §7 AC1/AC2)

Given `cv-match`'s real markdown structure (verified against `cv-v2.md`, NEXTON example): a name/title header, a summary paragraph, `## Expériences` (or `## Experience`) with `### Org — Role` sub-headings, a period line, and bullet lists with **bold lead-ins** (`- **Label** : detail`).

Required layout elements in the rendered PDF:
- **Header block** visually distinct from body text: name rendered larger/bold (reportlab `Heading1`-equivalent), title line beneath it in a secondary style — not the same font size as body paragraphs.
- **Section headings** (`## Expériences`, `## Compétences`, etc.) rendered as visually distinct headings (bold, larger than body, with spacing above) — not inline with surrounding text.
- **Sub-headings** (`### Org — Role`) visually distinguishable from top-level section headings (smaller than `##` but still bold/distinct from plain paragraph text) — a genuine two-level hierarchy, not everything collapsed to one style.
- **Bullet lists** rendered as actual bulleted list items (indented, bullet glyph or dash prefix, one item per line) — not run together as a single paragraph blob.
- **Bold inline emphasis** (`**text**`) rendered as bold text, not literal asterisks appearing in the PDF.
- **No visible raw markdown syntax** anywhere in the output (`#`, `##`, `**`, `- ` list markers must all be *converted*, never pass through literally).
- Single page or clean multi-page flow with consistent margins (reportlab default or explicit spec — Builder's choice, document it), page numbers optional (matches `pdf_create.py`'s existing default behavior).

**Explicitly NOT required for this ticket:** a second color, a photo, a two-column resume layout, custom fonts beyond what reportlab ships, or pixel-parity with any specific visual template. The bar is "clean, hierarchical, readable" — not "graphic-design polished."

### 6.2 Cover letter PDF — minimum bar (testable, §7 AC1/AC2)

Given `write-outreach`'s real markdown structure (verified against `outreach-v2.md`, NEXTON example): salutation (`Madame, Monsieur,`), 3–5 body paragraphs (~250–300 words per the skill's own target), closing (`Cordialement,` + name).

Required layout elements in the rendered PDF:
- Salutation line and closing/signature block visually separated from the body paragraphs (blank-line spacing at minimum; a distinct style is a nice-to-have, not required).
- Each paragraph rendered as its own visually separated block (paragraph spacing), not the whole letter as one run-on wall of text.
- **No visible raw markdown syntax** in the output.
- **No visible section markers from the source file** (`## 1. Lettre de motivation`, `## 2. Email recruteur...`, `---` dividers) — because the extractor (§4.1 item 3) must isolate only the cover-letter section, the recruiter-email and LinkedIn-message sections must not appear in the cover-letter PDF at all. This is a testable negative check (§7 AC3).
- Optional, not required: a header line with Nicolas's name/contact info repeated at the top (the source markdown as observed doesn't include one in the letter section itself — Builder should not invent contact-header content not present in the source; if the letter body itself contains a sign-off with name/phone/email, as observed in some real letters, that's sufficient).

## 9. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Markdown parsing is inherently more fragile than the fixed-JSON-block work of prior tickets — `cv-match`/`write-outreach` output varies per run (different heading text, occasional nested bullets, tables are not currently used by either skill but could appear). | Medium — a parser tuned only to the one example file read during this scope pass (NEXTON) could break on a differently-shaped real CV/letter. | Builder should test against **at least two** different real `applications/` folders (not just one) before calling AC1/AC2 satisfied — recommend NEXTON plus one more (e.g. UpSlide or Euronext) as a light robustness check, even though only one full end-to-end Notion-attach cycle (AC7) is strictly required. | The cover-letter section boundary (`## 1. Lettre de motivation` vs `## 1. Cover Letter` vs any other phrasing a future run might use) is a soft heuristic, not a hard contract — `write-outreach/SKILL.md` doesn't define numbered-section headings as a strict output-format guarantee, just as its own convention. | Medium — a future `write-outreach` run with slightly different heading phrasing could cause the extractor to grab the wrong section or the whole file. | Extractor should fail loudly (raise, not silently include extra sections) if it can't confidently find a `## 1...` boundary and a following `## 2...`/`---` boundary — consistent with this repo's established "fail loudly, never guess" style (`find_tailored_cv_section`'s behavior in `notion_cv_attachment.py` is the precedent).
